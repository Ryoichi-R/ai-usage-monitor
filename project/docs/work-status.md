# 作業状態監視（段階提供）

対象はCodex DesktopとClaude Codeだけ。利用枠表示と作業状態表示は独立して有効にできる。初期設定はOFF。設定画面の「全体設定」で各作業状態を表示し、「作業状態の接続設定…」からプロジェクト単位の設定例を作成する。

## 接続

配布物にはwork-status-bridge/を同梱する。ソースからの単純なdotnet buildにはBridgeの配布物を自動作成せず、接続例を生成するにはpublishを使う。

Codexは対象projectの.codex/hooks.jsonへhooksを限定追加して、本人がDesktopのReview hooksで確認する。Claudeは対象projectの.claude/settings.local.jsonへ限定追加する。既存のhooks・permissions・statusLineを置換しない。設定生成器が管理しているprojectでは、その生成器を使う。接続例の生成とコピーは設定ファイルの変更ではなく、実受信だけを接続の証拠とする。

Claudeのexec formには実行ファイルとargsを渡す。onFailure=continueの条件として、Desktop内CLIの2.1.295以上を設定例生成時に指定する。Codexのcommand hookはシェル文字列のため、Windows標準PowerShellのEncodedCommandでpathを安全に渡す。PowerShell 7/pwshや開発用SDKは通常のhook実行には不要。

WindowsのBridgeはWorkStatusBridges/v1/内容hashへ複製し、異なるビルドは別directoryに残す。Macは.app内を直接参照するため、.app移動時には再接続する。旧Bridgeの自動削除やフックの無断更新は行わない。

今回の配布形式はself-contained。.NET SDKや共有runtimeの別途導入を不要にする。NativeAOTも比較ビルドしたが、既存CoreのJSON reflection利用にIL2026/IL3050が発生したため採用していない。AOT化のための既存設定保存処理の変更は別途扱う。

## 状態と確認

通常表示は作業中・応答終了、Codexの質問待ち・権限確認中、Claude Codeの入力待ちとする。作業中だけは「作業中 3」のように半角スペースと件数を付ける。待機表示と応答終了に件数は付けず、未確認、中断履歴、状態不明、確認ボタンを表示しない。現在の作業中と待機を優先し、それらがなければ直近sessionのStopCandidate/Completedを応答終了と表示する。古い未確認通知の有無や確認操作に通常表示は連動しない。未受信、古い作業記録、中断後など、状態を判断できない場合は「—」とする。取得・保存に実際に失敗した場合の説明は残す。応答終了は応答が止まった記録を示し、作業成功の判定ではない。内部のStopCandidateを確定完了へ昇格させず、後続の作業イベントで作業中へ戻す。Claude Codeでは、接続設定画面の「確定完了の条件を確認するプロジェクトを選択…」で他のStopフック・有効なplugin・ファイル以外の管理ポリシーがないことを確認したprojectに限り、設定例のStop hookへ`--stop-may-complete`を付け、`stop_hook_active=false`のStopを確定完了（Completed）とする。確定後に同じturnのtool活動・入力待ち・再Stopが届いた場合は完了を取り消す。検査は接続時点の設定ファイルだけが対象で、skill frontmatterやserver-managed設定のフック、後から追加した設定は含まない。Stopフックを追加した場合は確認と設定例の作成をやり直す。Codexは常に停止候補とする。確定完了も応答終了と表示し、作業成功は保証しない。無更新、CPU低下、プロセス終了、idle_promptから完了を推測しない。

「確認済み」は押した時の通知だけに適用する。表示を消す、表示OFF、ウィジェットを隠す、終了する操作では未確認通知を消さない。クリック透過中は通知領域/メニューバーのprovider別確認操作を使う。

## 保存と障害

WorkStatus/state.jsonとevents/は既存アプリdata rootの配下。WindowsはLocalAppData/CodexUsageMonitor、MacはLibrary/Application Support/AiUsageMonitor。providerの利用枠・認証情報とは別のデータであり、PC間で同期しない。

状態はversion 1。必須項目はVersion、Sessions、Notices、ProcessedIds、AcknowledgedIds、Imports。通知ID集合、sessionの最終順序、確認済みIDを保存し、再起動で確認済みを復活させない。処理済みspoolはsnapshotを原子的に保存した後に整理する。未知protocol/不正eventは採用・削除せず警告する。同じ不正fileはその起動中に再処理せず、読取失敗は待機して再試行する。

event protocol 1の必須項目: Protocol、Id、Provider（CodexDesktop=0/ClaudeCode=3）、SessionId、TurnId、Kind、At（UTC）、DesktopVerified。OrderとCompletionRetractableは補助情報。session/turnはhashで、本文・ツール入力は含めない。

CodexはPreModelRequestも明示的な作業開始として受ける。新規チャットの初期送信でUserPromptSubmitやtoolイベントが届かない経路でも、モデル要求開始の受信後に作業中へ移せる。SessionStartだけでは作業中にしない。モデル要求の完了はturn全体の完了を意味しないためPostModelRequestでは応答終了へ移さず、Stop等の既存経路を維持する。model/session/turnのメタデータ以外の要求・応答・エラー本文は保存せず、subagent/未検証由来は既存の規則で除外する。未回答Codexカードはモデル要求が始まっても解除しない。更新したBridgeと設定例への切替後、本人のReview hooksと実受信を確認するまでは、この経路の実機受入済みとはしない。

Windowsでは、Claude Desktopの開始フックが届かなくても、終了を受信済みの同じセッションが新たに `busy` になったことを確認できれば、次の2秒間隔の取得で作業中に表示する。稼働中のClaude CodeプロセスのPID・開始時刻・Desktopの親プロセスを照合し、前回の終了より新しい状態だけを使う。この補助判定は画面表示だけに使う。入力待ち、終了通知、確認状態はフックから判定する。

Codexの質問カードはPreToolUseのrequest_user_input/request_user_input_asyncからQuestionOpenedを生成し、カード内の質問ごとにcall IDとindexのhashを記録する。同期質問はPostToolUseで解除する。非同期質問のaccepted=trueは回答を意味しないため解除せず、UserPromptSubmitの構造化question replyにあるquestionItemIdと対応する質問だけを解除する。

同じチャットで空白以外の通常メッセージが送信された場合は、そのチャットで送信前に開いたカードの入力待ちを解除する。これにより、カードが見当たらず通常メッセージで回答した場合も作業中表示に戻れる。後で開いたカード、別チャットのカード、形式を判定できない構造化回答は対象外。時刻付きの通常メッセージとカードの到着順が入れ替わっても、送信前のカードは再表示しない。旧版の時刻なしカードも、同じチャットの次の通常メッセージで解除する。保存するのは識別子と時刻などの状態情報のみで、質問文・選択肢・回答内容は保存しない。

ツール実行・Stop・通知の確認操作では未回答カードを消さない。SessionEndではそのチャットだけを閉じる。未回答のあるチャットは作業中件数へ加算せず入力待ちとして扱い、10分で自動解除しない。通常メッセージによる解除には、アプリ本体とCodexフックが参照するBridgeの両方を更新する。

Claude Codeのメインsessionでtool名が正確にAskUserQuestionであるPreToolUseを受信すると、既存の入力待ち状態へ移す。PostToolUse、または同じtoolのPostToolUseFailureを受信すると作業中へ戻す。応答終了への遷移はStopで別に判断する。質問文・選択肢・回答・エラー本文は参照/保存しない。失敗hookの設定例はAskUserQuestionだけをmatcherで対象とし、onFailure=continueを維持する。toolの開始前に拒否された場合など、公式CLIがPostToolUseFailureを発火しない経路まで解除を保証しない。このClaudeの待機判定は既存のWaiting/Activityを使い、Codexの未回答カード集合とは独立している。共通normalizerの変更はMac/Windows x64にも適用されるが、ARM64上の合成試験をそれらの実機受入には流用しない。公式hook仕様は https://code.claude.com/docs/en/hooks を参照する。

質問カードのtool名と構造化reply envelopeはCodex Desktopの互換性確認対象であり、公式hooks文書はこの専用経路の網羅を保証していない。形式が一致しない入力から回答済みを推測しない。Bridgeとアプリを同じ対応版へ更新して接続例を再適用し、本人のReview hooksと実カードの開閉の受信確認を終えるまで、実機対応済みとは扱わない。旧stateはQuestionIds関連の省略を空集合として読み込み、既存通知・確認IDを保持する。

上限はstdin 4MiB、event 4KiB、state 8MiB、error.log 1MiB。容量超過やstateの破損・未知schema・保存失敗では作業状態だけを停止/警告し、原本を空状態で上書きしない。ログはUTC、例外型、HResult、引数値やファイル名を含まないstackだけ。例外message/Dataや本文は保存しない。一般設定のfallbackを通知stateへ流用しない。

## 旧ウィジェットからの移行

旧版を本人が通常終了し、接続設定画面の「単体版の未確認通知を引き継ぐ…」で旧state.jsonのあるdirectoryを選択する。旧monitor.lockを取得できない場合は引き継がない。旧stateをdata rootのlegacy-backupsへhash付きで保持してから、新しいsnapshotへ通知だけを取り込む。同じ旧snapshotの再移行はno-op。旧state/eventsは変更・削除しない。旧版の確認済み操作を代行しない。

旧版へ戻す場合は、統合版を通常終了し、切替後に増えた通知と確認済み操作を確認してから接続先を戻す。古いbackupを単純に復元して新着を失わせない。逆変換による自動rollbackは未実装で、旧版と統合版のデータを保持して手動照合する。

## 開発時の隔離検証

Windows/Macの実行物に `--work-status-test-root <絶対path>` を渡すと、指定directory配下だけに設定と作業状態を保存する。利用枠取得、自動起動の変更、通常profileの読取を行わず、両providerの作業状態を表示する。Windowsは `<root>/CodexUsageMonitor/WorkStatus`、Macは `<root>/Library/Application Support/AiUsageMonitor/WorkStatus`。このmodeの合成eventによる表示確認は、実Desktopからの受信やMac実機受入の代わりにはならない。 隔離検証中のトレイ名は「AI Usage Monitor（隔離検証）」、設定画面は「AI Usage Monitor 設定 - 隔離検証」とし、設定画面もタスクバーへ表示して通常版との取り違えを防ぐ。この識別は共通hostの隔離mode限定で、通常版のトレイ名と設定画面のタスクバー非表示は維持する。 多重起動からの再表示通知では、非表示に加えて最小化されたwidgetも通常状態へ戻す。表示中の通常widgetに通知を繰り返しても、配置やnative layerを再作成しない。

設定生成器で管理されているプロジェクトでは、接続画面で作成した設定例を生成入力へ追加し、そのプロジェクトの正規手順で適用する。既存permissions・他hooks・statusLineを保持し、適用前のバックアップと差分をローカルへ保存する。生成器が対応する場合は、適用前後のDryRunや権限契約試験で追加内容と既存設定の保持を確認する。旧単体版や別Bridgeの監視hookがある場合は、旧設定と保存データを保持して切替内容を確認し、重複接続を避ける。生成器固有の引数や自動置換機能の対応は、そのプロジェクトの手順に従う。

## 自動受信と通知の確認

プロジェクトの設定を適用し、Codexでは本人のレビューを終えた後は、作業開始・ツール実行・停止等のイベントを自動受信する。利用者が毎回接続操作をする必要はない。ウィジェットは保存されたイベントを2秒間隔で取り込み、未受信/受信履歴/接続保証の説明は通常画面に表示しない。初期状態の待機中は、特定のチャットの稼働や接続の証明を意味しない。

中断/エラー/過去の状態記録とモニター独自の確認IDは保持するが、通常画面の表示対象にしない。必要な場合だけトレイのprovider別確認操作で保存済み通知を整理できる。Codex Desktopでの閲覧とは同期しないため、これを未読表示として使用しない。通常のSessionEndは待機へ移し、状態不明を増やさない。通常表示を簡略化しても、既存の状態・通知・確認済みIDを削除・自動確認しない。

トレイの各providerの確認操作は、そのメニューの生成時に表示対象だったIDだけを確認する。WindowsのNativeMenu.Openingが発生しない経路にも対応する。確認対象のIDは保存成功後だけ確認済みにし、新たな到着、別provider、取得/保存失敗時の未確認通知を巻き込まない。

Macのメニューバーは通知到着時にも同じNativeMenuを維持する。確認対象IDはメニューを開く前に更新し、表示中は固定する。確認項目の有効状態はIDとあわせて更新する。回帰テストでは、初回通知の有効化、実際のexporter click経路での確認、確認後の無効化、新着と別providerの保持を検証する。

2026-11-05のmacOS実機確認では、通常版で既存通知を確認済みにせずに通知メニューの開閉と有効状態を確認し、正常終了・再起動後も設定・state/events・hooks・自動起動を保持した。同じ変更のWindows x64/ARM64本体とWindows solutionはクロスビルドを確認した。Windows上でのUI・通知領域・UI Automationの実行確認は未実施。

### Claudeの長時間入力待ち

公式`AskUserQuestion`の開始を検出した場合だけ、省略可能な`InputPending`をevent/sessionへ保存し、回答成功または失敗、明示的な停止・session終了・次のpromptまで入力待ちを保持する。質問文・選択肢・回答・tool入力はこのmarkerへ保存しない。無関係なtool活動や再通知だけでは回答済みとしない。通常のRunning、権限待ち、旧snapshotのmarkerなしWaitingは従来の10分鮮度を維持する。取得元が利用不能な場合は入力待ちを保証しない。

markerは既存version 1の省略可能fieldで、旧snapshotを削除・初期化せず読み込める。markerなしの過去Waitingから質問を推測して変換しない。共通model/normalizerの変更はMacとWindows x64にも適用されるが、このWindows ARM64 PCの検証を他OSの実機受入とはしない。
隔離modeで「Claude Code連携…」を開いても、利用枠の表示を有効化したり、設定を保存したりしない。接続テストを無効にして取得delegateを渡さず、実CLIの取得は開始しない。通常modeでのClaude連携設定手順は維持する。

Codexの未回答質問カードは「質問待ち」、質問のないセッションの権限確認は「権限確認中」と表示する。別セッションで同時に発生した場合は両方を表示し、同じセッションに未回答質問がある場合は質問待ちを優先する。自動承認の権限確認も短時間表示されることがある。Claude Codeの質問失敗後の待機解除には、接続先にAskUserQuestion限定のPostToolUseFailureフックも適用する。
